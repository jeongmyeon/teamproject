## Technical Challenge & Troubleshooting ##
1. CLOVA Speech API 연동 시 데이터 전송 오류 해결 
- 문제 : CLOVA Speech API 가이드를 준수했음에도 서버 연동 오류 발생. 마감 임박으로 기능 제외 위기
- 원인 분석 : 오류 로그 정밀 분석 및 생성형 AI를 활용한 아키텍처별 설정값 다각도 검토. 분석 결과, 음성 파일을 JSON 형식이 아닌 Multipart/form-data로 전송해야 함을 발견
- 해결 : 전송 방식을 FormData 객체 활용으로 수정하여 연동 성공
- 성과 : 서비스 차별점 사수 및 성공적인 프로젝트 시연

2. 프론트엔드 상태 관리 최적화를 통한 서버 부하 절감
- 문제 : 특정 페이지 진입 시 동일한 API가 2호 이상 중복 호출되는 현상 발견. 불필요한 네트워크 트래픽 발생 및 서버 성능 저하 우려.
- 원인 분석 : 브라우저 개발자 도구 분석 결과, useEffect 훅의 의존성 배열 설정 마비로 인해 컴포넌트 리렌더링 시마다 API 요청 함수가 재실행되는 구조임을 파악.
- 해결 : useEffect 내 의존성 배열을 정확히 설정하여 초기 렌더링 시 단 1회만 호출되도록 로직 수정.
- 성과 : API 호출 횟수 감소 및 서버 자원 낭비 방지. 페이지 로딩 속도 개선

## 기술적 개전 : MyBaris -> Spring Data JPA 전환 ##
1. 패러다임의 전환 (SQL 중심 -> 객체중심)
- Problem : 반복적인 CRUD SQL 작성과 XML 매핑으로 인해 비즈니스 로직보다 SQL 관리에 과도한 리소스가 소요됨
- Solution : JPA의 ORM(Object-Relational Mapping)을 도입하여 자바 객체와 DB 테이블을 직접 매핑하고, 공통 인터페이스를 통해 반복적인 코드를 제거함
- Result : 데이터 접근 계틍의 코드량을 감소시키며, 도메인 모델 중심의 개발에 집중할 수 있게 됨

2. 다대다(N:M) 관계의 효율적 설계 및 관
- 연관 관계 매핑 : 'Recipes'와 'Ingredients' 간의 관계를 설정하여, 하나의 레시피가 여러 재료를 가지고 하나의 재료가 여러 레시피에 쓰이는 도메인 모델을 구현함
- JoinTable 활용 : JPA의 @ManyToMany와 @JoinTable 설정을 통해 중간 테이블을 자동으로 관리하도록 설계하여, 복잡한 다대다 쿼리 작성의 번거로움을 해결함
- 데이터 일관성 : 레시피 삭제 시 연관된 재료 매핑 정보가 안전하게 관리되도록 영속성 전이와 고아 객체 제거 기능을 검토하여 데이터 무결성을 확보함

3. 조회 성능 최적화 (N+1 문제해결)
- Problem : 레시피 상세 정보를 가져올 때 연관된 'category'와 'Ingredients' 목록을 각각 조회하여 발생하는 N+1 문제로 인해 DB 부하 발생
- Solution : JPQL의 Fetch Join을 사용하여 단 한 번의 쿼리로 레시피와 연관된 모든 객체 그래프를 메모리에 로드하도록 최적화함
- Result : 상세 페이지 로딩 시 발생하는 쿼리 횟수를 획시적으로 줄여 응답 속도를 개선
